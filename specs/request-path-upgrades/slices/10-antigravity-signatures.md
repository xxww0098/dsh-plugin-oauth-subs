# 10 Antigravity 思考签名表改 LRU（F7）

**波次** W4。**依赖**：09（按真实会话分桶，用的是同一个 Antigravity 目录）。**PR**：1 个。

## 解锁的契约

长会话里，旧工具调用的 thoughtSignature 不会再被淘汰，也就不会有旧的 functionCall 被改写成
文本、导致每一轮前缀都往后断一截。

基线（按调用序号统计的命中率）：0–119 次是 88–94%，120–159 次掉到 49.9%，160–199 次掉到
40.9%。现在每个会话 256 个键，每次调用占 2 个键，所以大约第 128 次调用开始淘汰。

## 接缝

改 `src/oauth/antigravity/request.ts` 的 `rememberThoughtSignature`（L93-110）、
`lookupThoughtSignature`，以及 L26-28 的常量：

- 签名桶按解析出的真实会话 id 分，依赖 08 和 09；回退 id 不共享签名历史。
- 每个会话最多 4096 个键。**get 和 set 都会刷新该键的位置（LRU）**，今天是先进先出，重复
  set 也不刷新。
- 最多保留 64 个会话。
- 全局签名文本总量上限 32 MiB，超出时淘汰最久没用的整个会话。

## 能跑 / 能看见

合成回放：一个会话连续 300 次工具调用，逐轮打印上游请求的前缀字节数，数字只增不减。

## 验证门禁

`test/antigravity.test.ts`：
- 在「session map reattaches thoughtSignature…」这组用例上扩展：300 次调用之后，最早那次调用的
  签名仍然挂在请求上，没有任何 functionCall 被改写成文本。
- 相邻两轮的上游请求前缀在字节层面稳定（后一轮以前一轮为前缀）。
- 会话之间互相隔离。
- 32 MiB 总量上限生效，淘汰按整个会话进行。

## 活测

最多 3 次。只在日志里记下真实签名的长度，不记内容。如果「典型签名大小 × 4096 × 64」明显
超过 32 MiB 的设想，按实测值调整总量上限，并记进 error.md。

## 下放给实施者的决定

LRU 的数据结构（利用 Map 的插入顺序即可）。

## 必须保持绿色

`npm test`，Antigravity 请求测试和缓存测试。

## 会改变本 slice 的反馈

15 的复测里，如果 120–199 桶的命中率还不到 85%：先排除 compaction 的影响，再把证据发给用户，
另开 slice 调查。
